## 1. uvicorn bind แค่ `127.0.0.1:8000` จริงไหม — จะแก้เมื่อไหร่

**ไม่ใช่ครับ** ตรวจบนเครื่องจริงแล้ว:

```
$ ss -tlnp | grep 8000
LISTEN 0 2048  10.99.199.73:8000  0.0.0.0:*  users:(("uvicorn",pid=31584))
```

bind ที่ IP ของ LAN อยู่แล้ว ไม่ใช่ loopback — PMG (`10.99.199.72`) เรียกได้ปกติและใช้งานจริงอยู่ทุกวัน

**ปัญหาจริงคือเรื่องเครือข่าย ไม่ใช่เรื่อง bind:**

```
119.46.226.124  →  2221 Mailcow · 2222 PMG · 2223 ai-train      (SSH เท่านั้น)
                   port 8000 ไม่ได้ forward ออกอินเทอร์เน็ต
```

ทดสอบแล้วยืนยัน: ต่อ `119.46.226.124:8000` จากข้างนอก **ไม่ติด** ซึ่งถูกต้องตามที่ควรเป็น
API นี้ไม่มี rate limit ระดับ public และ token เดียวเปิดทุก endpoint จึงไม่ควรเปิดตรงออกอินเทอร์เน็ต

**ทางเลือกที่เป็นไปได้ เรียงตามที่ผมแนะนำ:**

| | วิธี | ต้องใช้อะไร | ข้อดี/ข้อเสีย |
|---|---|---|---|
| **1** | Dashboard ย้ายมารันบนวงเดียวกัน | ขอเครื่อง/สิทธิ์จากพี่ที่ปรึกษา | เรียก `10.99.199.73:8000` ได้ตรง ไม่ต้องเปิดอะไรออกเน็ต |
| **2** | SSH tunnel ระหว่างพัฒนา | ไม่ต้องขอใคร ทำได้เลย | `ssh -p 2223 -L 8000:10.99.199.73:8000 admin@119.46.226.124` แล้วยิง `http://127.0.0.1:8000` |
| **3** | reverse proxy + TLS + subdomain | พี่ที่ปรึกษาต้องทำ DNS + nginx | ใช้ได้ยาว แต่ต้องมี auth ชั้นนอกเพิ่ม |

**ระหว่างนี้ใช้ข้อ 2 ได้ทันทีเลยครับ** — ผมทดสอบแล้วใช้ได้ ไม่ต้องแก้อะไรฝั่งเรา

## 2. `ai-train` จะมี subdomain `ai.vcapstone.com` ไหม

**ยังไม่มี และไม่ใช่สิ่งที่ทีม AI ตัดสินใจได้เอง** — DNS ของ `vcapstone.com` กับการ forward port
อยู่ที่พี่ที่ปรึกษา/ผู้ดูแลโครงสร้าง

เราไม่มีสิทธิ์ `sudo` บนเครื่องนี้ด้วยซ้ำ (ตอนนี้ใช้ cron แทน systemd อยู่)

**ถ้าจะขอ ควรขอพร้อมกันทั้งชุด** ไม่งั้นได้ subdomain มาก็ยังใช้ไม่ได้:
- DNS `ai.vcapstone.com` → เครื่อง `ai-train`
- reverse proxy + TLS
- **ชั้น auth ที่หน้า proxy** (เพราะ API นี้ token เดียวเปิดทุก endpoint รวมถึง `/model/activate` ที่สลับโมเดลได้)

ผมเสนอว่าให้ทีม Dashboard เป็นคนขอ เพราะเป็นฝ่ายที่ต้องใช้ — ผมช่วยเขียนเหตุผลเชิงเทคนิคให้ได้

## 3. `/model/feedback-label` + `/model/feedback-stats` — deploy หรือยัง

**ขึ้นแล้วครับ ใช้ได้เลย** ยิงทดสอบบนเครื่องจริงเมื่อกี้:

```
GET  /model/feedback-stats   200  {"labels_total":0,"labels_unique":0,
                                   "labels_required":50,"ready_to_retrain":false}
POST /model/feedback-label   พร้อมรับ
```

**สเปก `POST /model/feedback-label`**

```json
{
  "email_hash": "<raw_signals.email_hash ที่ได้จาก /analyze>",
  "true_label": "Phishing",
  "is_phishing": true,
  "analyst": "ชื่อคนตัดสิน"
}
```

`true_label` ต้องเป็นหนึ่งใน — ส่งค่าอื่นจะได้ **400 พร้อมรายการที่ถูกต้อง** ไม่ใช่ 500:

```
Business Email Compromise (BEC) · Malware Attachment · Phishing ·
Spam (High-Risk Source) · Normal
```

> `Normal` มีไว้ให้ analyst บอกว่า "จริง ๆ ไม่ใช่ภัย" — ไม่ใช่คลาสของโมเดล

header เหมือนทุก endpoint: `X-Security-Token: <token>` (**ไม่ใช่** `X-API-Key`)

**ตอนนี้ `labels_total = 0`** ยังไม่มีใครส่ง label เข้ามาเลยสักอัน
(label เอาไปใช้ทำอะไร — ดูข้อ 4 เปลี่ยนแล้ว)

## 4. `POST /model/retrain` — **ยกเลิกแล้ว เอาปุ่มออกได้เลย**

ตอบตรง ๆ ว่า**จะไม่สร้าง** ครับ ไม่ใช่ "ยังไม่เสร็จ" หรือ "รอคิว" — ตัดออกจากแผนถาวร (2026-08-26)

**ที่ปรับปุ่มให้แจ้งว่ายังใช้ไม่ได้ ถูกต้องแล้ว** ขอบคุณที่ไม่ปล่อย spinner ค้าง —
ตอนนี้เอาปุ่มออกได้เลย ไม่ต้องเก็บไว้รอ

### ทำไมถึงตัด ไม่ใช่เพราะไม่มีเวลา

ปุ่ม Retrain ตั้งอยู่บนสมมติฐานว่า *"โมเดลแยกประเภทได้อยู่แล้ว แค่ต้องข้อมูลใหม่"*
พอวัดจริงเมื่อ 26 ส.ค. พบว่าสมมติฐานนั้นผิด:

1. **73% ของจุดตัดสินใจในโมเดลคือคำถาม `ai_score > 99.99x ?`**
   คือมันแยกประเภทด้วยการจำเศษทศนิยมของ softmax เพราะทั้ง 4 คลาสมี `ai_score` เฉลี่ย 96–99 เท่ากันหมด
   คลาสพลิกได้ 7 ครั้งในช่วงคะแนนกว้าง 0.009

2. **label ตอนเทรนไม่ได้มาจากคนตัดสิน** — มาจาก "ไฟล์ต้นทาง + regex คำ" (n=952)
   คือถ้าอีเมลอยู่ในไฟล์ชื่อ BEC ก็เป็น BEC

> เทรนใหม่ด้วยโครงแบบนี้ = ได้โมเดลที่ทายป้ายปลอมได้แม่นขึ้น ไม่ใช่แยกประเภทได้ดีขึ้น
> ปุ่มที่กดแล้วได้ของแย่ลงโดยไม่มีใครรู้ อันตรายกว่าไม่มีปุ่ม

### ทำอะไรแทน

`attack_type_v2` — คิดประเภทจากหลักฐานที่ตรวจได้ (การปลอมตัว ลิงก์ ไฟล์แนบ) **ชี้ที่มาของคะแนนได้ทีละบรรทัด**
ขึ้น production แล้ว ส่งมาคู่กับ `attack_type` เดิมใน `raw_signals`

ขั้นต่อไปคือหาค่าน้ำหนักจาก label ที่คน**ตัดสินจริง** ด้วย logistic regression
(ได้ออกมาเป็นสมการ + odds ratio ที่อธิบายได้ ไม่ใช่ต้นไม้ 800 ต้น)

### แล้ว `/model/feedback-label` ยังต้องส่งไหม — **ต้อง และสำคัญกว่าเดิม**

label ที่ส่งเข้ามา**ไม่ได้เอาไป retrain แล้ว** แต่เอาไป 2 อย่างนี้แทน:

- วัดว่า `attack_type_v2` แม่นแค่ไหน**บนอีเมลจริงของบริษัท** (ตอนนี้ยังไม่มีตัวเลขนี้เลย)
- เป็นข้อมูลตั้งต้นของสมการข้างบน — ต้องการ **≥ 25 ตัวอย่างต่อประเภท**

`/model/feedback-stats` แก้ให้สะท้อนความจริงแล้ว:

```json
{
  "labels_total": 0, "labels_unique": 0, "labels_required": 50,
  "labels_purpose": "วัดความแม่นของ attack_type_v2 + fit สมการแยกประเภท (ไม่ใช่ retrain)",
  "retrain_endpoint": "cancelled",
  "ready_to_retrain": false      // deprecated — คงคีย์ไว้ชั่วคราวไม่ให้ UI เดิมพัง จะลบทีหลัง
}
```

> `ready_to_retrain` จะเป็น `false` ตลอดไปแล้ว อย่าเอาไปผูกกับ logic ใหม่
> บอกได้เมื่อไหร่ว่าเลิกใช้แล้ว ผมลบคีย์ออกให้

**สิ่งที่ช่วยได้มากที่สุดตอนนี้:** หน้าให้ analyst กดเลือกประเภทแล้วยิงเข้า `/model/feedback-label`
คอขวดคือ**คนตัดสิน ไม่ใช่ endpoint**

## 🆕 ของใหม่ที่ Dashboard เอาไปแสดงได้เลย

`/analyze` ส่ง 2 ฟิลด์ใหม่ใน `raw_signals` (additive ของเดิมไม่พัง)

```json
"attack_type_v2": {
  "attack_type": "Phishing", "score": 220, "confidence": "สูง",
  "reasons": ["spoof_lookalike(+45)", "link_text_mismatch(+45)", "spoof_brand(+40)", ...],
  "scores": {"Phishing": 220, "BEC": 25, "Spam": 0, "Malware": 0}
}
```

แสดง `reasons` ให้ analyst เห็นได้ตรง ๆ ว่า **ทำไมระบบถึงบอกว่าเป็นประเภทนี้** ซึ่งของเดิมตอบไม่ได้เลย
และจะช่วยให้เขาติด label ได้เร็วขึ้นด้วย

`attack_evidence` (20 ตัวแปร) ก็ส่งมาด้วย ถ้าอยากทำหน้า drill-down — รายละเอียดใน [`INTEGRATION.md`](INTEGRATION.md)

> ค่าใหม่ ๆ อาจเป็น `"Unknown Threat"` แปลว่า **เสี่ยงจริงแต่หลักฐานไม่พอบอกชนิด** ไม่ใช่ error
> ตอนนี้เกิดกับฟิชชิ่งจริงราว 57% — เป็นการบอกความจริง ดีกว่าเดามั่วแบบระบบเดิม
