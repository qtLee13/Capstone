# 06 · มาตรฐานการยืนยันตัวตนอีเมล — SPF / DKIM / DMARC

> ส่วนนี้เป็น **มาตรฐาน RFC จริง** ไม่ใช่การออกแบบของเรา
> เป็นกลุ่มสัญญาณเดียวในระบบที่มีเอกสารมาตรฐานรองรับเต็ม ๆ

---

## ⚠️ อัปเดตสำคัญ: DMARC เปลี่ยน RFC แล้ว (พ.ค. 2026)

| โปรโตคอล | RFC ที่ต้องอ้าง **ตอนนี้** | สถานะ |
|---|---|---|
| **SPF** | **RFC 7208** | Proposed Standard · ยังเป็นฉบับปัจจุบัน |
| **DKIM** | **RFC 6376** | Draft Standard · ยังเป็นฉบับปัจจุบัน |
| **DMARC** | **RFC 9989** ← *ไม่ใช่ 7489 แล้ว* | **Proposed Standard** (พ.ค. 2026) |
| DMARC — รายงานสรุป | RFC 9990 | aggregate reporting |
| DMARC — รายงานความล้มเหลว | RFC 9991 | failure reporting |

**อย่าอ้าง RFC 7489 เป็นมาตรฐานปัจจุบัน** — ฉบับนั้นเป็น *Informational* ตั้งแต่ปี 2015
และถูกแทนที่โดย RFC 9989 (เรียกกันว่า DMARCbis) แล้ว

> ✅ ข่าวดีสำหรับโปรเจกต์เรา: **RFC 9989 เข้ากันได้กับของเดิม** ระเบียน `v=DMARC1` ที่มีอยู่ยังใช้ได้
> การเปลี่ยนแปลงหลักคือเพิ่ม/เลิกใช้ tag บางตัว และเปลี่ยนจาก Public Suffix List
> ไปใช้วิธีไล่ต้นไม้ DNS (DNS tree walk) เพื่อหาระเบียนนโยบายให้แม่นขึ้น
> โค้ดฝั่งเราอ่านแค่ผล `pass`/`fail` จึงไม่ต้องแก้อะไร

**อ้างอิง**
- [RFC 9989 — DMARC (IETF Datatracker)](https://datatracker.ietf.org/doc/rfc9989/)
- [Specifications — dmarc.org](https://dmarc.org/resources/specification/)
- [M3AAWG Technology Summary: DMARC](https://www.m3aawg.org/TechnologySummaries/DMARC)

## ใช้ในระบบเราตรงไหน

สัญญาณสามตัวนี้อยู่ใน `raw_signals` และส่งให้ทีม .92 ไปคิดคะแนน:

```json
"spf_result": "fail", "dkim_result": "pass", "dmarc_result": "fail",
"auth_source": {"spf": "pmg", "dkim": "header", "dmarc": "pmg"}
```

### ทำไมต้องมี `auth_source`

ค่าเดียวกันอาจมาจากคนละที่ และ **น่าเชื่อถือไม่เท่ากัน**:

| แหล่ง | ความน่าเชื่อถือ | เหตุผล |
|---|---|---|
| `pmg` | สูงสุด | PMG ตรวจเองตอนรับเมล ปลอมไม่ได้ |
| `header` | ปานกลาง | อ่านจาก `Authentication-Results` ในเมล — **ผู้ส่งปลอม header นี้ได้** |
| `checkdmarc` | ต่ำ | เราไปถาม DNS เองทีหลัง ไม่ใช่ผลตอนส่งจริง |
| `none` / `not_checked` | — | ไม่มีข้อมูล ≠ ผ่าน |

ลำดับที่โค้ดใช้: **PMG > header > ตรวจเอง** และถ้าสองแหล่งขัดกันจะเขียน log เตือน
เพราะอาจแปลว่ามีคนปลอม header เข้ามา

> นี่เป็นจุดที่ตอบอาจารย์ได้ดีถ้าถูกถามเรื่อง **การไว้ใจข้อมูลนำเข้า**:
> เราไม่ได้เชื่อทุกอย่างที่อยู่ในตัวอีเมล เพราะผู้โจมตีเป็นคนเขียนมันมา

## ข้อจำกัดที่ต้องรู้ — ผ่าน SPF/DKIM/DMARC ≠ ปลอดภัย

**สำคัญมากถ้าอาจารย์ถามว่า "มี DMARC แล้วยังต้องมี AI ทำไม"**

| ข้อจำกัด | ผลที่ตามมา |
|---|---|
| ยืนยันแค่ว่า **โดเมนผู้ส่งเป็นเจ้าของจริง** | ผู้โจมตีจดโดเมนของตัวเอง ตั้ง SPF/DKIM ให้ครบ ก็ผ่านหมด |
| ไม่ได้ดูเนื้อหาเลย | เมลหลอกลวงที่ส่งจากโดเมนที่ตั้งค่าถูกต้อง = ผ่านทุกด่าน |
| ไม่ช่วยกับ **display name spoofing** | `From: "ฝ่ายบัญชี บริษัท ก" <attacker@gmail.com>` ผ่าน SPF ของ Gmail ได้สบาย |
| ไม่ช่วยกับบัญชีภายในที่ถูกยึด | เมลจากบัญชีจริงที่โดนแฮก ผ่านทุกอย่างโดยนิยาม |

สองข้อล่างคือเหตุผลตรง ๆ ที่ตารางน้ำหนัก BEC ของเราต้องมี
`spoof_display_name` (40) และ `spoof_freemail_corp` (25) — เป็นช่องว่างที่ RFC ปิดให้ไม่ได้

> ประโยคที่ใช้ตอบได้: *"SPF/DKIM/DMARC ตอบว่า 'ใครส่ง' ไม่ได้ตอบว่า 'เนื้อหาอันตรายไหม'
> BEC ส่วนใหญ่ผ่านทั้งสามอย่างเพราะผู้โจมตีใช้โดเมนของตัวเองที่ตั้งค่าถูกต้อง
> ระบบเราจึงต้องดูสัญญาณการปลอมตัวในระดับที่ RFC ไม่ครอบคลุม"*
