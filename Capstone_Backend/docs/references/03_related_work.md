## 1. BEC-Guard (Barracuda) — ใช้จริงในผลิตภัณฑ์

**Cidon, A., Gavish, L., Bleier, I., Korshun, N., Schweighauser, M., Tsitkin, A.**
*High Precision Detection of Business Email Compromise.*
USENIX Security Symposium 2019 · **Distinguished Paper Award**

### ทำไมสำคัญกับเรา

- เป็นระบบที่ **ใช้งานจริงใน production ตั้งแต่ กรกฎาคม 2017** (Barracuda Sentinel) ไม่ใช่แค่งานทดลอง
- ใช้ **supervised learning** จับ BEC แบบเรียลไทม์
- ระบุปัญหาตรงกับที่เราเจอ: BEC ไม่มี payload อันตรายชัดเจน + ปรับให้เข้ากับผู้รับแต่ละคน
  → ระบบกรองอีเมลทั่วไปจึงตรวจไม่เจอ

### เอาไปใช้ตอบอะไรได้

> *"การที่เราแยก BEC ออกมาเป็นคลาสของตัวเอง และใช้สัญญาณการปลอมตัวแทนสัญญาณจากลิงก์
> เป็นแนวทางเดียวกับ BEC-Guard ของ Barracuda ที่ได้ Distinguished Paper ใน USENIX Security 2019
> และใช้งานจริงในผลิตภัณฑ์"*

**อ้างอิง**
- [หน้า USENIX](https://www.usenix.org/conference/usenixsecurity19/presentation/cidon) · [PDF ฉบับเต็ม](https://www.usenix.org/system/files/sec19-cidon.pdf)

## 2. Detecting Credential Spearphishing in Enterprise Settings

**Ho, G., Sharma, A., Javed, M., Paxson, V., Wagner, D.**
USENIX Security Symposium 2017 (UC Berkeley)

### ทำไมสำคัญกับเรา

- ออกแบบ feature จาก **ลักษณะพื้นฐานของ spearphishing** แล้วใช้เทคนิคให้คะแนนความผิดปกติ
  แบบ non-parametric เพื่อ **จัดอันดับการแจ้งเตือน**
- ได้ false positive rate **0.004%** ภายใต้งบการแจ้งเตือน 10 ครั้งต่อวัน

### 🔑 บทเรียนที่ตรงกับปัญหาของเรามากที่สุด

งานนี้ไม่ได้ตั้งเป้าที่ "ความแม่นสูงสุด" แต่ตั้งเป้าที่ **"จำนวนการแจ้งเตือนที่คนตรวจไหวต่อวัน"**

เทียบกับของเรา: Stage 1 มี FP 25.2% → ถ้าองค์กรรับเมลวันละ 1,000 ฉบับ
จะมีเมลถูกกักผิด ~250 ฉบับต่อวัน ซึ่ง**ไม่มีทีมไหนตรวจไหว**

นี่เป็นกรอบที่ดีกว่าการเถียงว่า 25% "เยอะไปไหม" — ให้ถามว่า *ทีมตรวจไหวกี่ฉบับต่อวัน*
แล้วย้อนกลับไปหาว่า FP ต้องต่ำเท่าไหร่

**อ้างอิง**
- [หน้า USENIX](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/ho) · [PDF](https://people.eecs.berkeley.edu/~daw/papers/phish-usenix17.pdf)

## 3. ทำไมเลือก Logistic Regression ไม่ใช่ XGBoost

นี่เป็นการตัดสินใจเชิงออกแบบที่อาจารย์น่าจะถาม เพราะดูเหมือน "ถอยหลัง"

| | XGBoost (Stage 2 ปัจจุบัน) | Logistic Regression (ที่จะทำ) |
|---|---|---|
| ความแม่นบนข้อมูลที่มี | สูงกว่าโดยทั่วไป | ต่ำกว่า |
| ตอบว่า "ทำไม" | ต้องใช้ SHAP/LIME ตีความภายหลัง | **ค่าสัมประสิทธิ์คือคำตอบโดยตรง** |
| รูปแบบคำตอบ | ผลรวมค่าใบจากต้นไม้ 200 ต้น เขียนเป็นสมการไม่ได้ | `logit = b0 + b1·x1 + b2·x2 + …` |
| ตอบเป็น odds ratio | ไม่ได้ | ได้ — *"มี spoof_own_org แล้วโอกาสเป็น BEC เพิ่ม N เท่า"* |

**เหตุผลจริงที่เราเลือก** ไม่ใช่เพราะ logistic regression ดีกว่า แต่เพราะ:

1. เรามีข้อมูลป้ายที่คนตัดสินจริงน้อยมาก (เป้าหมาย ~400 แถว) — XGBoost 800 ต้นบนข้อมูลเท่านี้จะ overfit
2. **สิ่งที่โจทย์ต้องการคือคำอธิบาย ไม่ใช่ทศนิยมตำแหน่งที่สาม** — analyst ต้องเห็นว่าทำไมถึงถูกจัดเป็นประเภทนี้
3. Stage 2 เดิมพิสูจน์แล้วว่า "แม่นแต่อธิบายไม่ได้" นำไปสู่ปัญหา — 73% ของจุดตัดสินใจคือ `ai_score > 99.99x`
   ซึ่งไม่มีใครมองเห็นจนกระทั่งเราไปแกะต้นไม้ออกมาดู

> ประโยคที่ใช้ตอบได้: *"เราแลกความแม่นบางส่วนกับความสามารถในการตรวจสอบ
> เพราะระบบความมั่นคงปลอดภัยที่บอกไม่ได้ว่าทำไมถึงบล็อก คนจะเลิกเชื่อแล้วปิดมันทิ้ง"*
