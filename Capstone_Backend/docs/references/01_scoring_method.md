# 01 · วิธีให้คะแนนแบบถ่วงน้ำหนัก — มีใครทำแบบนี้บ้าง

> ตอบคำถาม: *"การเอาน้ำหนักหลายตัวมาบวกกันแล้วเทียบกับเกณฑ์ เป็นวิธีที่ยอมรับกันไหม"*

---

## 1. SpamAssassin — แบบอย่างที่ตรงกับเราที่สุด

**Apache SpamAssassin** เป็นตัวกรองอีเมลโอเพนซอร์สที่ใช้งานจริงมาตั้งแต่ปี 2001
และเป็นตัวที่ **PMG (Proxmox Mail Gateway) ในระบบเราใช้อยู่** ด้วย

### วิธีทำงาน — เหมือนของเราเกือบทั้งหมด

1. มีกฎหลายร้อยข้อ แต่ละข้อตรวจสิ่งหนึ่ง (เช่น หัวเรื่องมีคำว่า FREE, ส่งจาก IP ใน blacklist)
2. กฎที่ "ติด" จะให้คะแนนบวกหรือลบ
3. **รวมคะแนนทุกข้อ** แล้วเทียบกับเกณฑ์ (ค่าปริยาย 5.0)
4. เกินเกณฑ์ = สแปม

นี่คือสมการเดียวกับ `classify_attack_type()` ของเรา ต่างกันที่ SpamAssassin ตอบว่า
"สแปมหรือไม่" ส่วนเราตอบว่า "เป็นการโจมตีชนิดไหน" (คิดคะแนนแยกทีละชนิดแล้วเทียบกัน)

### 🔑 จุดที่สำคัญที่สุดสำหรับเรา — เขาก็เริ่มจากตั้งด้วยมือ

คะแนนของ SpamAssassin **ไม่ได้ตั้งด้วยมือถาวร** เขาหาค่าจากคลังจดหมายจริง:

| ช่วง | วิธีหาค่าน้ำหนัก |
|---|---|
| รุ่นแรก ๆ | ตั้งด้วยมือ |
| ถึงรุ่น 3.0.0 | **genetic algorithm** ปรับคะแนนทุกกฎบนคลัง spam/ham ขนาดใหญ่ (ใช้เวลาหลายชั่วโมง) |
| ตั้งแต่ 3.0.0 | **perceptron** (stochastic gradient descent) ทำงานเดียวกันแต่เร็วกว่ามาก (~15 วินาที) |

สูตรแปลงน้ำหนักที่เรียนรู้ได้กลับเป็นคะแนน:

```
score(weight) = -threshold * weight / bias
```

> **นี่คือเหตุผลที่เราตอบอาจารย์ได้อย่างมั่นใจ**
> เส้นทาง "ตั้งด้วยมือก่อน → หาค่าจากข้อมูลทีหลัง" ไม่ใช่การทำงานลวก ๆ
> แต่เป็นลำดับเดียวกับที่ระบบกรองอีเมลที่ใช้กันทั่วโลกเดินมา
> เราอยู่ขั้นแรก และมีสคริปต์สำหรับขั้นที่สองเตรียมไว้แล้ว
> (`fit_attack_type_equation.py` — เราเลือก logistic regression แทน perceptron เพราะรายงาน odds ratio ได้)

## 2. Microsoft Defender for Office 365 — คะแนนตัวเลขที่เปิดให้เห็น

ระบบอีเมลองค์กรของ Microsoft ติด **ตัวเลขคะแนน** ไว้ใน header ของทุกฉบับ

| ตัวชี้วัด | ช่วงค่า | ความหมาย |
|---|---|---|
| **SCL** (Spam Confidence Level) | −1, 0–9 | ระดับความมั่นใจว่าเป็นสแปม · 0–1 = ไม่ใช่สแปม · ≥5 = บริบทเชิงลบ · −1 = ข้ามการกรอง |
| **BCL** (Bulk Complaint Level) | 0–9 | ระดับความเป็น "เมลกระจาย" ยิ่งสูงยิ่งน่ารำคาญ · เกินเกณฑ์ที่ตั้งไว้ → เข้า Junk หรือ quarantine |

**เกี่ยวกับเรายังไง**
- ยืนยันว่าการ **ส่งคะแนนเป็นตัวเลขให้ระบบปลายทางตัดสินใจเอง** เป็นแนวปฏิบัติปกติ
  ซึ่งตรงกับที่ AI ส่ง `raw_signals` ให้ทีม .92 คิดคะแนนต่อ
- BCL ที่แยก "เมลกระจาย" ออกจาก "สแปมอันตราย" เป็นแนวคิดเดียวกับที่เราแยก
  `Spam (High-Risk Source)` ออกจาก `Phishing`

> ⚠️ ข้อควรระวังเวลาอ้าง: เอกสารของ Microsoft ระบุว่าปัจจุบัน **SCL ไม่ใช่ตัวตัดสินผลแล้ว**
> ระบบใช้การจัดหมวดและสัญญาณอื่นร่วมด้วย ค่า SCL เท่ากันอาจได้ผลตัดสินต่างกัน
> อย่าอ้างว่า "Microsoft ตัดสินด้วยคะแนนรวมอย่างเดียว"

**อ้างอิง**

- [Bulk complaint level (BCL) — Microsoft Learn](https://learn.microsoft.com/en-us/defender-office-365/anti-spam-bulk-complaint-level-bcl-about)

## 3. สิ่งที่ยัง **ไม่มี** อ้างอิง — ต้องพูดตรง ๆ

| สิ่งที่เป็นของเราเอง | ตอนนี้ตั้งจากอะไร |
|---|---|
| `link_text_mismatch = 45` | วัดอัตราการติด: ฟิชชิ่ง 5.4% · สแปม 1.5% · เมลปกติ 0.0% |
| `link_login_lure = 40` | ฟิชชิ่ง 5.3% · สแปม 0.9% · เมลปกติ 0.3% |
| `asks_credential = 35` | ฟิชชิ่ง 3.6% · สแปม 0.4% · เมลปกติ 0.0% |
| `has_urgency = 5` (ต่ำมาก) | ฟิชชิ่ง 16.8% · สแปม 16.5% → **แยกสองอย่างนี้ไม่ได้เลย** |
| `spoof_any = −40` (ติดลบ) | ฟิชชิ่ง 32.6% มีข้อความ unsubscribe เพราะลอกเทมเพลตจดหมายข่าว |
| `ATTACK_TYPE_MIN_SCORE = 35` | ที่ 25 สัญญาณอ่อนตัวเดียวก็ตัดสินได้ ซึ่งหลวมเกินไป |

**หลักที่เราใช้ตั้ง:** สัญญาณที่ *แยกประเภทได้ชัด* ได้น้ำหนักมาก
สัญญาณที่ติดทั้งสองประเภทพอ ๆ กันได้น้ำหนักน้อย ถึงแม้จะ "ดูน่าสงสัย" ก็ตาม

นี่เป็นเหตุผลที่ป้องกันได้ แต่ **ไม่ใช่การฟิตจากข้อมูล** — อย่าเรียกว่า "เทรน"

## สรุปสำหรับตอบอาจารย์

**ถาม:** วิธีบวกน้ำหนักแบบนี้เชื่อถือได้ไหม
**ตอบ:** เป็นวิธีที่ SpamAssassin ใช้มา 20 กว่าปี และ PMG ในระบบเราก็ใช้อยู่

**ถาม:** ตัวเลขน้ำหนักมาจากไหน
**ตอบ:** เราตั้งเองจากอัตราการติดที่วัดบนข้อมูลจริง 8,612 ฉบับ ยังไม่ได้ฟิตจากป้ายที่คนตัดสิน
ซึ่งเป็นขั้นเดียวกับที่ SpamAssassin เคยอยู่ก่อนเปลี่ยนไปใช้ GA/perceptron
เรามีสคริปต์ทำขั้นนั้นแล้ว รอข้อมูลป้ายจากผู้ตรวจ
