# คำถามสำหรับพี่ที่ให้โปรเจกต์ — เรื่อง Dashboard ควรแสดงอะไร

**เตรียมเมื่อ:** 2026-08-10 · **ใช้กับ:** นัดคุยกับพี่ที่บริษัท

---

## หลักการก่อนถาม

**ถามเฉพาะสิ่งที่เราตัดสินใจเองไม่ได้** — เรื่องเทคนิค (ใช้ React ไหม, สีอะไร, เก็บ DB ยังไง) เราตัดสินใจเองได้หมด
สิ่งที่**มีแต่พี่เท่านั้นที่ตอบได้** คือ **"ของจริงในองค์กรทำงานยังไง"** — คำถามข้างล่างเลือกมาเฉพาะแบบนั้น

**เอาของไปโชว์ด้วย** อย่าไปมือเปล่า:
1. หน้าจอที่ทำไว้แล้ว (screenshot 3-4 หน้า)
2. รายการข้อมูลที่ระบบผลิตได้จริง (ตารางในหัวข้อ "ภาคผนวก" ท้ายเอกสาร)
3. บอกให้ชัดว่า *"ตอนนี้เราเดาเอง อยากให้พี่ช่วยยืนยันว่าตรงกับของจริงไหม"*

---

## 🔴 กลุ่ม 1 — คำถามสำคัญที่สุด (ถ้าได้ตอบแค่ 3 ข้อ ให้ถามกลุ่มนี้)

### 1.1 ใครเป็นคนใช้ Dashboard นี้จริง ๆ และมีกี่คน?

> *"ตอนนี้พวกผมออกแบบไว้ 3 บทบาท — **SOC** (ดูอีเมลที่ถูกกัก/ตัดสินว่าปล่อยหรือบล็อก), **IT** (ตั้งกฎ ดูโมเดล), **Admin** (จัดการผู้ใช้ ดู audit log)
> อยากทราบว่าในองค์กรจริงมีคนแยกบทบาทแบบนี้ไหมครับ หรือเป็นคนเดียวทำทุกอย่าง?"*

**ทำไมสำคัญ:** ถ้าจริง ๆ มี IT คนเดียวดูแลทั้งระบบ การแยก 3 บทบาท 14 หน้าจอ = ออกแบบเกินความจำเป็นมาก และหน้าที่ควรมีจริงจะเหลือแค่ 3-4 หน้า

---

### 1.2 พออีเมลถูกกัก (quarantine) ขั้นตอนจริงเป็นยังไง?

ถามเป็นข้อย่อย:
- คนรับปลายทาง **รู้ตัวไหม**ว่ามีเมลถูกกัก หรือเงียบไปเลย?
- ถ้าเขาไม่ได้รับเมลสำคัญ เขา**ร้องเรียนทางไหน** (โทร / เปิด ticket / ทัก IT)?
- ใครเป็นคนกด **"ปล่อย"** — IT ตัดสินเอง หรือต้องขออนุมัติ?
- ปกติใช้เวลานานแค่ไหนกว่าจะปล่อย (ชั่วโมง/วัน)?

**ทำไมสำคัญ:** ตอบแล้วจะรู้ว่า**หน้าจอหลักควรเป็นหน้าไหน** — ถ้าคนร้องเรียนเข้ามาเป็นรายฉบับ หน้าที่ต้องดีที่สุดคือ **"ค้นหาอีเมลของคนนี้"** ไม่ใช่หน้ากราฟสรุปสวย ๆ ที่พวกผมทำไว้

---

### 1.3 ระหว่าง "เมลร้ายหลุดเข้าไป" กับ "เมลดีโดนกักผิด" อันไหนแย่กว่ากันสำหรับองค์กร?

ถามให้เป็นรูปธรรม:
> *"ถ้าเลือกได้อย่างเดียว — ยอมให้ฟิชชิ่งหลุด 1 ฉบับต่อ 100 หรือยอมให้อีเมลลูกค้าโดนกักผิด 1 ฉบับต่อ 100 ครับ?"*

**ทำไมสำคัญ:** นี่คือคำถามที่**กำหนดเลขทั้งระบบ** — ตอนนี้เกณฑ์ตัดสินใจ (30/60/80) พวกผมตั้งเอง ไม่มีที่มาจากธุรกิจเลย
ถ้าพี่บอกว่า *"เมลลูกค้าโดนกักผิดคือหายนะ"* → ต้องดัน threshold ขึ้นและยอมให้จับได้น้อยลง · ถ้าตรงข้ามก็ปรับกลับกัน
**เป็นการตัดสินใจเชิงธุรกิจ ไม่ใช่เชิงเทคนิค — พวกผมตัดสินแทนไม่ได้**

---

## 🟡 กลุ่ม 2 — คำถามที่ทำให้ Dashboard ตรงกับงานจริง

### 2.1 ตอนนี้ (ก่อนมีระบบเรา) องค์กรดูอะไรอยู่?
> *"มีรายงานหรือหน้าจออะไรที่ดูอยู่ประจำไหมครับ ขอดูตัวอย่างได้ไหม (ปิดข้อมูลลับได้)"*

**ทำไมสำคัญ:** ของที่เขาใช้อยู่แล้วคือคำตอบที่ดีที่สุดว่า *"อะไรมีประโยชน์จริง"* — ดีกว่าเราคิดใหม่จากศูนย์

### 2.2 มีตัวเลขอะไรที่ต้องรายงานผู้บริหาร / ทำเป็นประจำไหม?
เช่น สรุปรายเดือน จำนวนภัยที่บล็อกได้ แนวโน้ม
**ทำไมสำคัญ:** ตัวเลขพวกนี้ควรอยู่หน้าแรก ส่วนตัวเลขที่ไม่มีใครใช้ควรตัดทิ้ง

### 2.3 พอเจออีเมลน่าสงสัย 1 ฉบับ คนดูอยากรู้อะไรเป็นอันดับแรก?
ให้พี่เรียงลำดับ:
`ใครส่ง` · `ส่งถึงใครบ้าง` · `หัวข้อ/เนื้อหา` · `ทำไมระบบตัดสินแบบนี้` · `เคยเจอแบบนี้มาก่อนไหม` · `ลิงก์/ไฟล์แนบข้างใน`

**ทำไมสำคัญ:** ตอนนี้หน้ารายละเอียดโชว์คะแนนเป็นตัวเลข 4 ตัว ซึ่งอาจไม่ใช่สิ่งที่คนใช้อยากเห็นเลย
> เราเพิ่งทำ **"เหตุผลที่ระบบตัดสิน"** ได้แล้ว (เช่น *"SPF ไม่ผ่าน · โดเมน Reply-To ไม่ตรงกับผู้ส่ง"*) — ลองถามว่าอันนี้มีประโยชน์กว่าตัวเลขไหม

### 2.4 อีเมลที่โดนกัก ต้องเก็บไว้นานแค่ไหน? ลบทิ้งได้เมื่อไหร่?
**ทำไมสำคัญ:** เกี่ยวกับพื้นที่เก็บ + กฎหมาย (PDPA) และเป็นสิ่งที่เราเดาเองไม่ได้

### 2.5 ข้อมูลอะไรที่ **ห้าม** แสดงบนหน้าจอ / ห้ามเก็บ?
> *"ตอนนี้ระบบเก็บหัวข้อและเนื้อหาอีเมลไว้ด้วย ซึ่งเป็นข้อมูลส่วนบุคคล — มีข้อกำหนดเรื่องนี้ไหมครับ ใครมีสิทธิ์เห็นเนื้อหาเต็มบ้าง?"*

**ทำไมสำคัญ:** ไฟล์ที่พี่ให้มายัง censor บางส่วน แปลว่ามีกฎอยู่แล้ว ควรถามให้ชัดก่อนที่ระบบจะโชว์ของจริง

---

## 🟢 กลุ่ม 3 — คำถามที่กระทบตัว AI โดยตรง

### 3.1 จะมีคนกดบอกระบบไหมว่า "ตัดสินผิด"?
> *"พวกผมทำปุ่มให้เจ้าหน้าที่กดแก้ผลได้ แล้วเอาไปสอนโมเดลให้ฉลาดขึ้น
> แต่ต้องสะสมประมาณ 50 ฉบับถึงจะเทรนใหม่ได้ — ในทางปฏิบัติจะมีคนกดจริงไหมครับ วันหนึ่งน่าจะกดกี่ฉบับ?"*

> 📝 **อัปเดต 2026-08-26:** คำถามนี้เปลี่ยนกรอบแล้ว — เรายกเลิก `/model/retrain` ถาวร
> (Stage 2 แยกประเภทด้วย `ai_score` เป็นหลัก เทรนซ้ำไม่ช่วย) label จึงไม่ได้เอาไปเทรน
> แต่เอาไป **วัดความแม่น** และ **หาค่าน้ำหนักของสมการแยกประเภท**
> คำถามที่ควรถามจริง ๆ คือ: *"ให้ analyst ตรวจกี่ฉบับถึงจะเชื่อตัวเลขความแม่นได้ครับ"*

**ทำไมสำคัญ:** ระบบเรียนรู้ต่อเนื่องทั้งหมด**ตั้งอยู่บนสมมติฐานว่าจะมีคนกด** ถ้าจริง ๆ ไม่มีใครมีเวลากด ต้องออกแบบใหม่ (เช่น เรียนจากการกด "ปล่อยเมล" แทน ซึ่งเป็นงานที่เขาทำอยู่แล้ว)

### 3.2 อีเมลภาษาไทยจริงในองค์กรมีสัดส่วนเท่าไหร่? ขอตัวอย่างได้ไหม?
> *"ตอนนี้ข้อมูลไทยที่ใช้สอนโมเดลเป็นข้อความที่**แปลด้วยเครื่อง**จากอีเมลอังกฤษ ไม่ใช่อีเมลไทยที่คนไทยเขียนจริง
> พวกผมทดสอบแล้วเจอปัญหา: อีเมลไทยปกติที่ขึ้นต้นว่า **'เรียนคุณสมชาย'** ระบบตีเป็นฟิชชิ่งทันที (คะแนนพุ่งจาก 0 เป็น 98) เพราะข้อมูลฝรั่งสอนว่า 'การเจาะจงชื่อ = การโจมตี' แต่ในไทยมันคือมารยาทปกติ
> ถ้าได้อีเมลไทยจริงมาสัก 100-200 ฉบับ (censor ได้) จะแก้จุดนี้ได้ตรงมากครับ"*

**ทำไมสำคัญ:** เป็นข้อจำกัดที่ใหญ่ที่สุดของโมเดลตอนนี้ และ**แก้ได้ด้วยข้อมูลเท่านั้น** เก่งแค่ไหนก็แก้เองไม่ได้

### 3.3 องค์กรเคยโดนอีเมลหลอกแบบไหนจริง ๆ บ้าง?
**ทำไมสำคัญ:** ระบบแบ่งภัยเป็น 4 ประเภท (ฟิชชิ่ง / สแปม / **หลอกโอนเงินแอบอ้างผู้บริหาร (BEC)** / ไฟล์แนบมัลแวร์)
ถ้าองค์กรเจอแค่ 2 ประเภท การแยก 4 ประเภทก็ไม่มีประโยชน์ · และ **BEC เป็นประเภทที่โมเดลเราแม่นน้อยที่สุด** ถ้าองค์กรเจอบ่อยต้องทุ่มแก้ตรงนี้ก่อน

## ❌ อย่าถามคำถามพวกนี้ (เราตัดสินใจเองได้ / เสียเวลาพี่)

| อย่าถาม | เพราะ |
|---|---|
| *"ควรใช้สีอะไร ธีมไหนดี"* | เราตัดสินใจเองได้ |
| *"ควรเก็บ DB ยังไง / ใช้ React ไหม"* | เรื่องเทคนิคของเรา |
| *"อยากได้ฟีเจอร์อะไรบ้างครับ"* | กว้างไป จะได้คำตอบลอย ๆ **ให้ถามเป็นสถานการณ์แทน** เช่น *"ถ้าเมล CEO โดนกัก พี่จะทำยังไงต่อ"* |
| *"Dashboard ควรมีกี่หน้า"* | เป็นผลลัพธ์จากคำตอบข้ออื่น ไม่ใช่คำถามตั้งต้น |

## 💡 เทคนิคการถามให้ได้คำตอบที่ใช้ได้จริง

1. **ถามเป็นสถานการณ์ ไม่ถามเป็นฟีเจอร์**
   ❌ *"อยากได้หน้าจออะไร"* → ✅ *"สมมติเช้านี้เมลใบเสนอราคาจากลูกค้าโดนกัก พี่จะรู้ได้ยังไง แล้วทำอะไรต่อ"*

2. **ให้เลือก ดีกว่าให้คิดเอง**
   ❌ *"อยากให้แสดงอะไร"* → ✅ *"3 อย่างนี้ อันไหนสำคัญสุด: จำนวนเมลวันนี้ / รายการเมลที่รอตัดสินใจ / แนวโน้ม 30 วัน"*

3. **เอาหน้าจอจริงไปให้ติ** — คนติของที่เห็นได้ง่ายกว่าจินตนาการจากศูนย์
   *"หน้านี้พวกผมทำไว้แบบนี้ ตรงไหนไม่ตรงกับงานจริงบ้างครับ"*

4. **ถามว่าอะไร "ไม่ต้องมี" ด้วย** — คนมักบอกแต่สิ่งที่อยากได้เพิ่ม แต่สิ่งที่ควรตัดทิ้งมีค่าพอกัน

5. **จดคำตอบเป็นข้อ ๆ แล้วทวนกลับให้พี่ยืนยันตอนจบ** — กันเข้าใจคลาดเคลื่อน

## 📎 ภาคผนวก — เอาตารางนี้ไปโชว์พี่

> *"นี่คือข้อมูลที่ระบบผลิตออกมาได้จริงครับ อยากให้พี่ช่วยดูว่าอันไหนมีประโยชน์ อันไหนไม่ต้องแสดงก็ได้"*

### ระบบรู้อะไรเกี่ยวกับอีเมลแต่ละฉบับ

| ข้อมูล | ตัวอย่าง |
|---|---|
| เวลา / ผู้ส่ง / ผู้รับ / หัวข้อ | `billing@invoice-service.tk` → `finance@corp.com` |
| **คะแนนความเสี่ยง 0–100** | `80` |
| **ผลการตัดสิน** | ปล่อยผ่าน / เตือน / **กักไว้** / บล็อก |
| **ประเภทภัย** | ฟิชชิ่ง · สแปม · **หลอกโอนเงิน (BEC)** · ไฟล์แนบมัลแวร์ |
| **เหตุผลที่ตัดสินแบบนั้น** 🆕 | *"SPF ไม่ผ่าน · โดเมน Reply-To ไม่ตรง · พบไฟล์แนบอันตราย .js"* |
| คะแนนแยกรายด้าน | เนื้อหา 10 · ลิงก์ 0 · โดเมนผู้ส่ง 4 · ไฟล์แนบ 20 · ภาษาหลอกลวง 2.5 |
| ลิงก์ในเมล + ระดับความมั่นใจ | ยืนยันอันตราย / น่าสงสัย / ปกติ |
| ไฟล์แนบ + ชนิด | `.js` (อันตราย) |
| ผลตรวจตัวตนผู้ส่ง | SPF / DKIM / DMARC |
| ชื่อเสียง IP ผู้ส่ง | 0–100 *(หรือ "ตรวจไม่ได้")* |

### ระบบทำอะไรได้บ้าง

| ทำได้ | |
|---|---|
| ดูอีเมลที่ถูกกัก + **ปล่อยออกไปได้** | ✅ |
| ตั้งกฎเอง (บล็อกผู้ส่ง / รายชื่อที่ไว้ใจ) | ✅ |
| กดบอกว่า **"ระบบตัดสินผิด"** เพื่อสอนโมเดล | ✅ |
| ดูข้อมูลโมเดล AI + ความแม่น (แยกอังกฤษ/ไทย) | ✅ |
| ย้อนโมเดลกลับเวอร์ชันเก่าถ้ารุ่นใหม่แย่ลง | ✅ |
| บันทึกว่าใครทำอะไรในระบบ (audit log) | ✅ |

### สิ่งที่ยังทำไม่ได้ (บอกพี่ตามตรง)

- **ไม่ได้สแกนไฟล์แนบจริง** — ดูแค่ชนิดไฟล์ ไม่มีการตรวจไวรัสในตัวไฟล์
- **ตรวจการปลอมชื่อผู้ส่งยังไม่ได้** (เช่น โดเมนคล้ายของจริง `paypa1.com`) — กำลังจะทำ
- **ข้อมูลไทยเป็นข้อความแปลด้วยเครื่อง** ไม่ใช่อีเมลไทยจริง (ดูข้อ 3.2)
- **BEC (หลอกโอนเงิน) แม่นน้อยสุด** เพราะตัวอย่างจริงมีน้อย
