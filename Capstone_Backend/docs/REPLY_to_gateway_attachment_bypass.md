# ตอบทีม Gateway — ช่องโหว่ไฟล์แนบไม่มี `filename=` (แก้แล้ว)

**จาก:** ทีม AI Server (.94) · **วันที่:** 2026-08-10 · **สถานะ:** ✅ แก้ + ทดสอบแล้ว ⏳ รอ deploy

---

## สรุปสั้น

**รายงานของคุณถูกต้อง 100% และเป็นช่องโหว่ด้านความปลอดภัยจริง** ทำซ้ำได้ทันที

การทดลองของคุณคือวิธีที่ถูกต้องที่สุด — **ยิงเมลจริง 2 ฉบับที่ต่างกันแค่ `--attach-name`** แล้วเทียบผล ทำให้ตัวแปรเดียวโดดออกมาชัดเจน ไม่มีอะไรกำกวม

| การทดลองของคุณ | ผล |
|---|---|
| ไม่ใส่ `--attach-name` | `type=[] malware=False` → **score 7.09 · Normal** ❌ |
| ใส่ `--attach-name "invoice.js"` | `type=['.js'] malware=True` → **score 80 · Malware Attachment** ✅ |

**ไฟล์เดียวกัน มัลแวร์เดียวกัน ต่างกันแค่ผู้โจมตี "ไม่ใส่ชื่อไฟล์" — ซึ่งทำได้ฟรี**

---

## 1. ทำซ้ำฝั่งเราแล้ว — ตรงกันเป๊ะ

```
เคส                              attachment_type   has_malware
มี filename (ปกติ)               ['.js']           True
มีแต่ name= ไม่มี filename        ['.js']           True     ← ชั้นนี้ผ่านอยู่แล้ว
🔴 ไม่มีทั้งคู่ (เคสของคุณ)        []                False    ← ช่องโหว่
```

> 💡 **หมายเหตุ:** ข้อเสนอชั้นที่ 2 ของคุณ (`Content-Type: name=`) **ระบบทำอยู่แล้ว** — `get_filename()` ของ Python อ่านให้ทั้ง `Content-Disposition: filename=` และ `Content-Type: name=` · **ช่องโหว่จริงคือชั้นที่ 3 ตามที่คุณชี้เป๊ะ**

---

## 2. 🛠️ แก้แล้ว — ทำครบทั้ง 4 ชั้นที่คุณเสนอ

ทำเป็นฟังก์ชันเดียว `ep.attachment_ext(part)` ไล่หาเป็นชั้น ชั้นล่างปลอมยากขึ้นเรื่อยๆ:

| ชั้น | วิธี | สถานะ |
|---|---|---|
| ① | `Content-Disposition: filename=` | ✅ เดิมมีอยู่แล้ว |
| ② | `Content-Type: name=` | ✅ เดิมมีอยู่แล้ว (Python อ่านให้) |
| ③ | **`Content-Type` MIME เอง** | 🆕 **เพิ่มใหม่ — ปิดช่องโหว่ของคุณ** |
| ④ | **magic bytes ของเนื้อไฟล์** | 🆕 **เพิ่มใหม่ด้วย** (คุณบอกว่าแม่นสุดแต่ยาก — ทำเลยครับ) |

**MIME ที่แมป (ชั้น ③)** — 27 ชนิด เช่น
`application/javascript` → `.js` · `application/x-msdownload` → `.exe` · `application/x-msdos-program` → `.exe`
`application/x-iso9660-image` → `.iso` · `application/vnd.rar` → `.rar` · `application/x-ms-shortcut` → `.lnk` …

**magic bytes (ชั้น ④)** — อ่าน 16 ไบต์แรก
`MZ` → `.exe` · `PK\x03\x04` → `.zip` · `Rar!\x1a\x07` → `.rar` · `7z\xbc\xaf'\x1c` → `.7z`
`\xd0\xcf\x11\xe0` → `.doc` (OLE2 พาหะ macro) · `\x1f\x8b` → `.gz` · `BZh` → `.bz2` · `MSCF` → `.cab` · `L\x00\x00\x00` → `.lnk`

> 🔒 **ปลอดภัยตามนโยบายโปรเจกต์:** อ่านเนื้อไฟล์**ในหน่วยความจำเท่านั้น ไม่เขียนลงดิสก์ ไม่รันไฟล์** · ข้ามไฟล์ใหญ่เกิน 2 MB (กันเปลือง RAM)

---

## 3. ผลทดสอบหลังแก้

```
เคส                                                    attachment_type   has_malware
① มี filename (ปกติ)                                   ['.js']           🔴 True
① มีแต่ name=                                          ['.js']           🔴 True
② ไม่มีชื่อ แต่ MIME บอก  ← เคสของคุณ                   ['.js']           🔴 True   ✅ ปิดแล้ว
③ ไม่มีชื่อ + MIME โกหกว่า octet-stream (payload = EXE)  ['.exe']          🔴 True   ✅ magic bytes จับได้
③ ไม่มีชื่อ + MIME โกหก (payload = ZIP)                 ['.zip']          🔴 True   ✅
ปลอดภัย: PDF มีชื่อไฟล์                                 ['.pdf']          🟢 False
ปลอดภัย: ข้อความล้วนไม่มีไฟล์แนบ                        []                🟢 False
```

**ชั้น ④ ทำให้ปิดได้แม้ผู้โจมตีจะโกหก MIME ด้วย** — ไม่ใส่ชื่อไฟล์ + ตั้ง `Content-Type: application/octet-stream` ก็ยังจับได้จากเนื้อไฟล์จริง

---

## 4. ✅ ตรวจแล้วว่าไม่กระทบของเดิม (สำคัญ)

`attachment_risk` เป็น feature ของโมเดล Stage 2 — ถ้าเปลี่ยนวิธีตรวจแล้วค่าไม่ตรงกับตอนเทรน จะเกิด **train/serving skew** (บั๊กที่โปรเจกต์นี้เจอมา 4 ครั้ง ทุกครั้งไม่มี error ให้เห็น มีแต่ผลลัพธ์ผิด) จึงวัดก่อนแก้:

| ตรวจ | ผล |
|---|---|
| อีเมลในคลังเทรนที่ `has_malware` จะเปลี่ยน | **0 / 2,400 ฉบับ (0.00%)** |
| ไฟล์แนบที่ไม่มีชื่อไฟล์ในคลังเทรน | **0** |
| `body` ที่ป้อน BERT เปลี่ยนไหม | **0 / 800 ฉบับ — เหมือนเดิมเป๊ะ** |

→ **ไม่ต้องเทรนโมเดลใหม่ · `ai_score` ไม่เพี้ยน · deploy ได้เลย**

**ทำไมคลังเทรนถึงไม่มีเคสนี้เลย:** มัลแวร์จริงในธรรมชาติ*ต้องการ*ให้เหยื่อกดเปิด เลยใส่ชื่อไฟล์ล่อ (`invoice.pdf.exe`) เสมอ — **ช่องโหว่นี้จึงเป็นการโจมตีที่จงใจเลี่ยงระบบตรวจ ไม่ใช่พฤติกรรมมัลแวร์ทั่วไป** ซึ่งเป็นเหตุผลที่ข้อมูลเทรนมองไม่เห็น และต้องมีคนทดลองแบบที่คุณทำถึงจะเจอ

## 5. สิ่งที่จะเปลี่ยนใน `raw_signals`

`attachment_type` จะมีค่าในเคสที่เมื่อก่อนเป็น `[]`:

```jsonc
// ก่อน — ไฟล์แนบ .js ไม่มีชื่อไฟล์
{ "attachment_type": [], "has_malware": false }

// หลัง
{ "attachment_type": [".js"], "has_malware": true }
```

**ไม่มีการเปลี่ยน contract** — ชื่อ/ชนิด field เหมือนเดิมทุกอย่าง ฝั่งคุณกับ .92 ไม่ต้องแก้โค้ด

> เพิ่มค่าใหม่ 1 แบบ: `".unknown"` — ใช้เมื่อ *"เป็นไฟล์แนบแน่ๆ แต่ระบุชนิดไม่ได้เลยทั้ง 4 ชั้น"*
> **ไม่นับเป็น `has_malware`** (ไม่มีหลักฐานว่าอันตราย) แต่ทำให้เห็นว่ามีไฟล์แนบอยู่ ไม่หายเงียบเหมือนเดิม
> ถ้าฝั่ง .92 อยากให้ `.unknown` มีน้ำหนักเล็กน้อยในการคิดคะแนน ก็สมเหตุสมผล — ไฟล์แนบที่ปกปิดชนิดตัวเองมีเจตนาน่าสงสัย

## 6. 🙏 ขอบคุณ + ข้อสังเกตท้ายเรื่อง

รายงานนี้มีค่ามากครับ เพราะเป็นช่องโหว่ที่ **ฝั่งเรามองไม่เห็นเลย** — ทั้ง log และคะแนนดูปกติทุกอย่าง อีเมลได้ `Normal` อย่างสงบ ไม่มี error ไม่มีอะไรผิดสังเกต

**สิ่งที่ทำให้จับได้คือวิธีทดสอบของคุณ** — ส่งเมลจริงผ่านระบบเต็ม แล้วเปลี่ยนตัวแปรทีละตัว · ถ้าดูแต่โค้ดอย่างเดียวคงไม่มีใครสงสัยว่า `get_filename()` จะคืนค่าว่างได้

**เจอเคสอื่นอีกส่งมาได้เลยครับ** โดยเฉพาะแนวนี้ — *"สิ่งที่ควรโดนจับ แต่ผ่านไปได้เงียบๆ"* เพราะเป็นประเภทที่มองจากในระบบไม่เห็น

> 💡 **ถ้าอยากทดสอบเพิ่ม** ลองแนวนี้ได้: ไฟล์แนบซ้อนในไฟล์แนบ (`message/rfc822`), ชื่อไฟล์ที่มี RTL override (`invoice‮gpj.exe` แสดงเป็น `invoice.jpg`), หรือ zip ที่มีนามสกุลปลอมข้างใน — ยินดีตรวจให้ทุกเคส
