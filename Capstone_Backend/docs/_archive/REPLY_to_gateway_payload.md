# ตอบทีม mail server (.92) — เคส payload เป็น JSON ทำให้ทุกฉบับได้ ai ≈ 100

**จาก:** ทีม AI Server (10.22.1.94) · **วันที่:** 2026-07-22 · **สถานะ:** ✅ ทำซ้ำอาการได้ + ใส่ตัวกันแล้ว + deploy แล้ว (2026-08-04)

---

## สรุปสั้น

**การวินิจฉัยของคุณถูกต้อง 100%** เราทำซ้ำอาการได้เป๊ะทุกฟิลด์

แต่มีจุดหนึ่งต้องแก้ความเข้าใจ: **โค้ดที่ยิงเข้า `/assess` ไม่ได้อยู่ฝั่ง AI ครับ** — เราถอดออกไปตั้งแต่ 2026-07-16 ตามที่ตกลงสถาปัตยกรรมกันไว้ (AI ตอบ `raw_signals` กลับ Gateway ตรงๆ ไม่ push ไป .92 เอง)

> ตรวจแล้วทั้ง codebase: ไม่มี `requests.post(.../assess)` เหลืออยู่เลย · มีแค่ comment เก่าค้างอยู่บรรทัดเดียวซึ่งลบให้แล้ว

**จุดที่ผิดจริงคือ "ใครก็ตามที่ยิงเข้า `POST /analyze` ของเรา"** ไม่ใช่ตอนยิงออกไป `/assess` — เพราะ AI อยู่ **ก่อน** `/assess` ในสายการทำงาน ถ้า input ที่เข้ามาผิด ทุกอย่างหลังจากนั้นก็ผิดตามหมด

---

## 1. ทำซ้ำอาการได้ตรงทุกฟิลด์

ยิง JSON ของ mailbox API เข้า `/analyze` ของเรา เทียบกับส่ง `.eml` จริง:

| ฟิลด์ที่คืนกลับ | ส่ง `.eml` จริง ✅ | ส่ง JSON ทั้งก้อน ❌ |
|---|---|---|
| `subject` | `"URGENT: Verify your account now!"` | **`"No Subject"`** |
| `sender_domain` | `"evil-bank.xyz"` | **`"unknown"`** |
| `sender_email` | `"security-alert@evil-bank.xyz"` | **`""`** |
| `body_text` | เนื้อเมลจริง | **`'{"status": "success", "folder": ...'`** |
| `raw_ai_score` | 100.0 | 100.0 |

ตรงกับที่คุณรายงานทุกช่อง — **ยืนยันว่ากลไกเป็นอย่างที่คุณวิเคราะห์**

### ทำไม ai ถึงได้ ~100 ทุกฉบับ

ตัวแกะอีเมลไม่เจอ header สักตัว (เพราะบรรทัดแรกเป็น `{`) → คืน `subject = "No Subject"`, `sender = unknown` และเอา **JSON ทั้งก้อนเป็น body**
BERT จึงได้ข้อความที่มี `"folder":"quarantine"` + เนื้อ phishing ที่ฝังใน `raw_email` ปนกันมั่ว → ยิงคะแนนสูงให้แทบทุกฉบับ

**และมันไม่ error เลย** — นี่คือส่วนที่อันตรายที่สุด ทุกอย่างดูปกติในล็อก มีแต่ตัวเลขที่ผิด

---

## 2. 🛡️ สิ่งที่เราแก้ฝั่ง AI — ทำให้มัน "ดังตอนเข้า"

เราแก้ปัญหาที่รากไม่ได้ (โค้ดที่ยิงมาไม่ได้อยู่กับเรา) แต่**เรารับผิดชอบได้ว่าจะไม่ยอมรับ input ที่ผิดแบบเงียบๆ อีก**

เพิ่มตัวตรวจ payload ก่อนเข้าโมเดล:

| กรณี | ผลลัพธ์ใหม่ |
|---|---|
| `.eml` ปกติ | ✅ `200` ทำงานตามปกติ |
| **JSON ที่มีฟิลด์ `raw_email`/`raw_message`/`eml`/`content`** | 🔴 **`400 invalid_email_payload`** + บอกชื่อฟิลด์ที่ควรส่งมาแทน |
| JSON อื่นๆ | 🔴 `400 invalid_email_payload` |
| ข้อความล้วนไม่มี header | 🟡 `200` แต่ log warning ไว้ |
| payload ว่าง | 🔴 `400` |

ตัวอย่าง response ที่จะได้:
```json
{
  "detail": {
    "error": "invalid_email_payload",
    "message": "payload เป็น JSON ไม่ใช่อีเมลดิบ — เนื้อเมลจริงอยู่ในฟิลด์ 'raw_email' กรุณาส่งเฉพาะค่าในฟิลด์นั้นมาเป็น text (ถ้าส่ง JSON ทั้งก้อน จะได้ subject='No Subject' / sender='unknown' และ ai_score จะเพี้ยนโดยไม่มี error)",
    "expected": "field 'text' ต้องเป็นอีเมลดิบรูปแบบ RFC 5322 (มี header From/Subject/Received)"
  }
}
```

### ⚠️ สิ่งที่ต้องเตือนก่อน deploy

**นี่เป็นการเปลี่ยนพฤติกรรม** — งานไหนที่ตอนนี้ส่ง JSON เข้ามา จะเปลี่ยนจาก "ได้คะแนนเพี้ยน" เป็น **"ได้ error 400"**

เราเลือกทางนี้เพราะ **quarantine เมลดีโดยไม่มีใครรู้ แย่กว่า error ที่เห็นชัด** — แต่ถ้าทีมไหนอยากให้ผ่อนเป็นแค่ warning ก่อนจนกว่าจะแก้ฝั่ง caller เสร็จ **บอกได้ครับ เปลี่ยนให้ทันที**

> เราตั้งใจ**ไม่**แกะฟิลด์ `raw_email` ให้อัตโนมัติ เพราะการซ่อมให้เงียบๆ = บั๊กเดิมยังอยู่แค่มองไม่เห็น และทำให้ AI ต้องผูกกับรูปแบบ API ของทีมอื่น

## 3. 🔍 เรื่อง loop — เห็นด้วยและอยากชวนคิดต่อ

ข้อสังเกตของคุณเรื่อง *"เมลใน quarantine ถูกอ่านกลับมา re-assess"* น่าจะเป็นต้นเหตุที่แท้จริง เพราะ payload มี `"folder":"quarantine"` อยู่ในตัวมันเอง = อ่านมาจากกล่อง quarantine แน่นอน

**คำถามที่อยากให้ช่วยตรวจ:** งานที่อ่าน mailbox API แล้วยิงเข้า `/analyze` เป็นงานอะไรครับ — cron re-scan / ปุ่มใน Dashboard / หรือสคริปต์ทดสอบ?
รู้ตัวนี้แล้วจะชี้ได้ว่าควรแก้ที่ไหน (และจะได้รู้ว่าทีมไหนต้องแก้)

**ข้อเสนอกัน loop:** ถ้าจำเป็นต้อง re-scan จริง ขอให้ส่ง `.eml` ที่แกะจากฟิลด์ `raw_email` มา และ**อย่าเอาผลลัพธ์กลับไปเขียนทับกล่องเดิม** — ไม่งั้นรอบถัดไปจะอ่านของที่ตัวเองเขียนไปอีก

## 4. 🙏 เรื่อง `POST /parse` — ขอบคุณมาก แต่ขอเสนอกลับด้าน

ข้อเสนอเรื่อง endpoint กลางดีมากครับ แต่ขอเสนอให้ **AI เป็นฝ่ายให้บริการแทน** ด้วยเหตุผลเดียว:

**ตัวแกะอีเมลของ AI ต้องเหมือนตอนเทรนโมเดลเป๊ะๆ** — ถ้าใช้ตัวแกะคนละตัว ค่าที่ป้อนโมเดลจะไม่ตรงกับตอนเทรน (train/serving skew) ซึ่งเป็นบั๊กที่โปรเจกต์นี้เจอมาแล้ว 4 ครั้ง และทุกครั้ง**ไม่มี error ให้เห็นเลย** มีแต่ผลลัพธ์ที่ผิด

> ครั้งที่หนักสุด: ตัวแกะอีเมลทำภาษาไทยเสียหายก่อนถึงโมเดล ทำให้**อีเมลนัดประชุมภาษาไทยธรรมดาได้ ai_score 98.81** ทั้งที่ข้อมูลตอนเทรนถูกต้องทุกอย่าง

**ข้อเสนอ:** ถ้าทีมคุณต้องการ signals จาก `.eml` เราเปิด `POST /parse` ให้ได้เลยครับ (รับ raw `.eml` → คืน `sender/subject/body/attachments/spf/dkim/dmarc`) โดยใช้ตัวแกะตัวเดียวกับที่โมเดลใช้ **รับประกันว่าตรงกันเสมอ**

ส่วน `parse_signals()` ของทีมคุณยังใช้ต่อได้เต็มที่สำหรับงานฝั่ง scoring ที่ไม่เกี่ยวกับโมเดล — แค่อย่าให้เป็นตัวเตรียม input ให้ AI

**สนใจให้ทำ `/parse` ไหมครับ? ถ้าเอา บอกมาว่าอยากได้ field อะไรบ้าง เดี๋ยวทำให้**
