# แจ้งทีม Gateway — เพิ่ม field `abuseipdb_measured` ใน `raw_signals`

**จาก:** ทีม AI Server (10.22.1.94) · **วันที่:** 2026-07-22 · **สถานะ:** ✅ deploy ขึ้น production แล้ว

> **TL;DR** — ไม่ต้องแก้อะไรก็ยังทำงานได้เหมือนเดิม 100% · แต่มี field ใหม่ 1 ตัวที่**แนะนำให้เอาไปใช้** เพราะมันแก้จุดบอดของการคิดคะแนนจาก IP

---

## 1. ปัญหาที่เจอ

เดิม `raw_signals.abuseipdb_score` เป็นตัวเลข 0–100 (สูง = IP อันตราย) แต่ **ค่า `0` มีสองความหมายปนกันอยู่**:

| ค่า | ความหมายที่ 1 | ความหมายที่ 2 |
|---|---|---|
| `abuseipdb_score: 0` | ✅ ตรวจแล้ว **IP สะอาดจริง** | ❓ **ตรวจไม่ได้** — ไม่มี public IP ใน `Received` / API ล่ม / คีย์หมดโควตา |

**ผลเสีย:** ถ้าฝั่ง scoring ให้เครดิต "IP สะอาด" กับค่า 0 → **อีเมลที่เราตรวจ IP ไม่ได้เลยจะได้เครดิตฟรี** ซึ่งเป็นการเอียงไปทางปล่อยภัยผ่าน (fail-open)

เคสนี้เกิดจริงบ่อยกว่าที่คิด — อีเมลที่ผ่าน fast path (คะแนน AI ต่ำมาก) เราจะ**ข้ามการเช็ค IP ทั้งหมด**เพื่อความเร็ว ค่าที่ส่งไปจึงเป็น 0 ทุกครั้งทั้งที่ไม่เคยตรวจ

---

## 2. สิ่งที่เพิ่ม

```jsonc
{
  "raw_signals": {
    "abuseipdb_score":    0,        // เหมือนเดิมทุกอย่าง — เป็นตัวเลขเสมอ ไม่เคยเป็น null
    "abuseipdb_measured": false,    // 🆕 true = ตรวจแล้วจริง · false = ไม่ได้ตรวจ/ตรวจไม่สำเร็จ
    ...
  }
}
```

**ตารางการตีความ:**

| `abuseipdb_measured` | `abuseipdb_score` | แปลว่า | ควรทำ |
|---|---|---|---|
| `true` | `0` | ตรวจแล้ว **IP สะอาด** | ให้เครดิตได้ |
| `true` | `> 0` | ตรวจแล้ว **IP มีประวัติเสีย** | บวกคะแนนความเสี่ยงตามค่า |
| `false` | `0` | **ไม่รู้** (ไม่มี IP / API ล่ม / ข้าม fast path) | **อย่าให้เครดิต** ให้ถือเป็นกลาง |

---

## 3. ที่อยากขอให้แก้ฝั่ง scoring (ถ้าสะดวก)

ถ้าตอนนี้โค้ดเป็นประมาณนี้:
```python
if abuseipdb_score == 0:
    risk -= 5            # ⚠️ ให้เครดิตทั้งที่อาจไม่เคยตรวจ
elif abuseipdb_score > 50:
    risk += 30
```

แนะนำเปลี่ยนเป็น:
```python
if not raw.get("abuseipdb_measured", True):
    pass                 # ไม่รู้ = ไม่บวกไม่ลบ (ปลอดภัยกว่าเดาว่าสะอาด)
elif abuseipdb_score == 0:
    risk -= 5            # ตรวจแล้วสะอาดจริง ค่อยให้เครดิต
elif abuseipdb_score > 50:
    risk += 30
```

> `.get("abuseipdb_measured", True)` — ใส่ default เป็น `True` ไว้ เผื่อเจอ response รุ่นเก่าที่ยังไม่มี field นี้ จะได้ทำงานเหมือนเดิม

**ถ้ายังไม่แก้ก็ไม่พัง** — field เดิมทุกตัวยังเหมือนเดิมเป๊ะ นี่เป็นการ "เพิ่ม" ไม่ใช่ "เปลี่ยน"

---

## 4. 🙏 สิ่งที่อยากขอจาก PMG (ถ้ามี) — จะช่วยได้เยอะ

ตอนนี้เราหา sender IP จาก `Received` header ซึ่ง **upstream ปลอมได้** และบางฉบับก็หาไม่เจอเลย (นี่คือสาเหตุหลักที่ `abuseipdb_measured: false`)

**ถ้า PMG ส่ง connection-level IP จริงมาให้** เราจะเช็ค AbuseIPDB ได้แม่นขึ้นมาก และ `measured: false` จะลดลงเยอะ:

```json
{
  "text": "<raw email>",
  "recipient": "user@corp.com",
  "spf_result": "fail",
  "dkim_valid": false,
  "dmarc_result": "fail",
  "sender_ip": "45.83.12.9"      // 🙏 optional — ไม่ส่งก็ fallback ไปอ่าน header เหมือนเดิม
}
```

(เคยเสนอไว้ในโน้ตรอบก่อนแล้ว ขอย้ำอีกรอบเพราะรอบนี้เห็นผลกระทบชัดขึ้น)

---

## 5. หมายเหตุ: มีการเปลี่ยนโมเดล Stage 2 ด้วย (ไม่กระทบ API)

โมเดลจำแนกประเภทภัยถูกเทรนใหม่ **ตัด feature `dmarc_fail` ออก** เพราะตรวจพบว่าในข้อมูลเทรนมันไม่มีข้อมูล DMARC จริงอยู่เลย (ค่าที่วัดได้มีแค่ `fail` ทั้งหมด ส่วนค่า `0` คือ "หา DNS record ไม่เจอ" ไม่ใช่ "ผ่าน")

**ไม่กระทบทีม Gateway เลย:**
- `raw_signals.dmarc_result` **ยังส่งเหมือนเดิม** (และยังยึด PMG เป็นหลักตามที่ตกลงกันไว้) — แค่ไม่ได้ถูกใช้เป็น input ของโมเดลแล้ว
- `attack_type` ยังเป็น 4 ค่าเดิม: `Phishing` / `Spam (High-Risk Source)` / `Business Email Compromise (BEC)` / `Malware Attachment` / `Normal`
- ไม่มี field ไหนหายไป
